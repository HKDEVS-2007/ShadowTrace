# PART 2 — PRODUCT REQUIREMENTS DOCUMENT

## 2. Investigation Reports & Export

### 2.1 Purpose

The Reports module allows users to generate structured investigation reports from the data stored in ShadowTrace.

A report should present an organized summary of:
- Investigation information.
- Uploaded evidence.
- Evidence integrity references.
- CSV processing results.
- Normalized event statistics.
- Detection analysis.
- Findings.
- Supporting event references.

Reports must be scoped to the selected investigation.

### 2.2 Functional Requirements

**FR-01: Investigation Report Preview**

Users must be able to preview a report before generating or exporting it.

The preview should include:

1. Report title.
2. Investigation ID.
3. Investigation title.
4. Investigation description.
5. Investigation status.
6. Report generation timestamp.
7. Evidence summary.
8. SHA-256 evidence hashes.
9. Processing summary.
10. Event summary.
11. Detection analysis summary.
12. Findings summary.
13. Supporting event references.

**FR-02: Report Generation**

The system must generate reports using saved database records.

Reports must not rely on hardcoded example information.

The report must identify its associated investigation.

**FR-03: Evidence Summary**

Include:
- Evidence ID.
- Original filename.
- File size.
- Upload timestamp.
- SHA-256 hash.
- Processing status.

Original evidence metadata must remain distinguishable from derived analysis results.

**FR-04: Processing Summary**

Include:
- Total CSV rows.
- Valid rows.
- Invalid rows.
- Duplicate rows.
- Processing status.

**FR-05: Detection Summary**

Include:
- Analysis run information.
- Rules evaluated.
- Events analyzed.
- Findings generated.
- Analysis timestamp.

**FR-06: Findings Summary**

Include:
- Finding ID.
- Rule name.
- Severity.
- Status.
- Description.
- Detection timestamp.
- Supporting event references.

**FR-07: Report Export**

The initial release should support a structured report format such as PDF.

The report should be readable, professionally formatted, and suitable for academic project demonstrations.

PDF generation should happen through the backend using the report data stored in SQLite.

**FR-08: Data Export**

Users must be able to export:

- Normalized events as CSV.
- Findings as CSV.
- Evidence metadata as CSV.

Each export must be scoped to the selected investigation.

**FR-09: Export Validation**

The system must handle:
- Missing investigations.
- Empty datasets.
- Missing processing records.
- Missing analysis records.
- Invalid report requests.
- Export generation errors.

The report must clearly distinguish unavailable information from information showing zero results.

### 2.3 Report Data Model

Recommended `reports` fields:

- `id`
- `investigation_id`
- `report_name`
- `generated_at`
- `file_path`
- `report_status`

Optional fields can be introduced with team approval.

Generated report files must be stored outside the public frontend directory.

The browser must receive a controlled download response rather than an absolute server filesystem path.

## 3. Audit Trail & Activity History

### 3.1 Purpose

The Audit Trail records important actions performed within ShadowTrace.

It provides a chronological history of significant application activities.

The module helps users understand when important investigation operations occurred and which records were affected.

The initial implementation is an application-level activity log. It must not be described as a tamper-proof or cryptographically immutable audit system.

### 3.2 Functional Requirements

**FR-10: Record Important Activities**

The system should record:

- Investigation created.
- Investigation updated.
- Investigation archived.
- Evidence uploaded.
- Evidence integrity verification performed.
- CSV processing completed.
- Detection analysis executed.
- Finding status changed.
- Finding note added.
- Report generated.
- Data export generated.

**FR-11: Activity Metadata**

Each activity record should include:

- Activity ID.
- Investigation ID, where applicable.
- Action type.
- Description.
- Timestamp.
- Related record type.
- Related record ID.

If authenticated user information is available in the existing application, the responsible user may also be recorded.

Do not invent an authentication system solely for this feature.

**FR-12: Activity History Listing**

Users must be able to view activities associated with an investigation.

The list should be chronological.

**FR-13: Activity Filtering**

Support filtering by:
- Action type.
- Date range.
- Related record type.

**FR-14: Activity Details**

Users should be able to inspect an activity record.

Display:
- Activity type.
- Description.
- Timestamp.
- Investigation.
- Related record.

**FR-15: Audit Data Handling**

Audit records should not be silently modified through normal application workflows.

If correction or administrative maintenance is necessary, it must follow an explicit, documented process.

The application should use controlled database operations and appropriate permissions where available.

# PART 3 — API REQUIREMENTS

Member 4 owns these endpoints:

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/investigations/<id>/report` | Preview investigation report data |
| POST | `/api/investigations/<id>/reports` | Generate report |
| GET | `/api/reports/<id>` | Get report details |
| GET | `/api/investigations/<id>/exports/events` | Export normalized events |
| GET | `/api/investigations/<id>/exports/findings` | Export findings |
| GET | `/api/investigations/<id>/exports/evidence` | Export evidence metadata |
| GET | `/api/investigations/<id>/activity` | List activity history |

### 4.1 Example Report Preview Response

```json
{
  "ok": true,
  "data": {
    "investigation_id": 1,
    "title": "Suspicious Login Investigation",
    "evidence_count": 2,
    "event_count": 120,
    "findings_count": 3,
    "generated_at": "2026-11-14T10:00:00"
  }
}
```

### 4.2 Example Activity Response

```json
{
  "ok": true,
  "data": [
    {
      "id": 1,
      "investigation_id": 1,
      "action_type": "EVIDENCE_UPLOADED",
      "description": "A CSV evidence file was uploaded.",
      "related_record_type": "evidence",
      "related_record_id": 1,
      "timestamp": "2026-11-14T10:00:00"
    }
  ]
}
```

### 4.3 Export Responses

CSV exports should use appropriate response headers and filenames.

Use safe generated filenames.

Do not expose internal filesystem paths.
